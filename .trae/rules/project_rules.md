# 项目开发规则 (Project Rules)

本规则集旨在让 Trae 在开发过程中 **避免重复出现相同问题**，提高代码质量与开发效率。Trae 将自动遵循。

## 一、问题预防与追溯机制（核心：杜绝重复错误）

### 错误日志记录
- 项目根目录维护一个 `.trae/known_issues.md` 文件，记录历史上出现过的问题、原因及解决方案。
- Trae 在执行任何代码修改前，必须先读取该文件，检查本次操作是否会引发已记录的问题。
- 若可能重复，Trae 应主动提醒用户，并提供替代方案。

### 修改前检查清单
每次对现有代码进行修改时，Trae 必须执行以下检查：
1. 是否修改了公共函数/接口？如果是，检查所有调用点。
2. 是否更改了数据库字段？如果是，检查相关实体、DAO、SQL 映射。
3. 是否引入了新的依赖？如果是，说明原因并确认无许可证冲突。
4. 是否影响了现有单元测试？如果是，同步更新测试用例。

### 禁止盲目复制粘贴
- 不得从其他文件或网络直接复制大段代码而不理解逻辑。如需复用，应提取为公共方法或组件，并添加注释说明来源。

## 二、代码质量规范

### 命名一致
- 类名：大驼峰（PascalCase）
- 方法/变量：小驼峰（camelCase）
- 常量：全大写下划线分隔（UPPER_SNAKE_CASE）
- 数据库字段：小写下划线分隔（snake_case）
- 前后端字段命名风格必须统一，避免映射错误。

### 注释与文档
- 所有 `public` 方法必须有 Javadoc/JSDoc 注释，说明参数、返回值、异常。
- 复杂业务逻辑必须添加行内注释，解释“为什么这么做”，而非“做了什么”。
- 修改代码时，必须同步更新相关注释和文档。

### 代码长度限制
- 单个方法不超过 50 行（含注释）。
- 单个类不超过 500 行（特殊情况需注释说明）。
- 超过限制时必须拆分。

### 禁止硬编码
- 所有配置项（URL、路径、常量、环境相关）必须提取到配置文件（如 `application.yml`、`.env`）。
- 业务规则中的数值（如税率、加班倍数）必须配置化，不得写死。

## 三、错误处理与日志

### 统一异常处理
- 后端使用 `@ControllerAdvice` 全局异常处理，不得在 controller 中随意 try-catch。
- 前端使用统一错误拦截器，统一提示用户。

### 日志规范
- 使用 SLF4J + Logback（后端），console + 文件输出（前端）。
- 日志级别：info（正常流程）、warn（可恢复异常）、error（不可恢复异常）。
- 禁止在生产环境输出 `System.out.println()` 或 `console.log` 调试信息。
- 关键操作（增删改、登录、支付）必须记录日志，包含操作人、时间、内容。

### 空指针预防
- 链式调用前必须判空，可使用 `Optional` 或 `Objects.requireNonNull`。
- 方法参数校验：使用 `@NotNull`、`@NotBlank` 等注解，或在方法首部断言。

## 四、单元测试与集成测试

### 测试覆盖率
- 核心业务逻辑（Service 层）覆盖率不低于 80%。
- 工具类、公共方法覆盖率 100%。
- Trae 在生成代码后，应同步生成对应的单元测试（JUnit/Jest）。

### 测试数据
- 使用独立测试数据库，不得使用生产数据。
- 测试数据应通过 `@Sql` 脚本或 `@DataJpaTest` 自动构造，测试完成后自动回滚。

### 测试命名
- 格式：`方法名_应做什么_预期结果`，例如 `calculateSalary_withOvertime_shouldReturnCorrectAmount`。

## 五、数据库操作规范

### 事务管理
- 所有涉及多表写操作的方法必须添加 `@Transactional`，并指定 `rollbackFor = Exception.class`。
- 查询方法使用 `@Transactional(readOnly = true)` 提高性能。

### SQL 性能
- 禁止在循环中执行数据库查询/更新（N+1 问题），必须使用批量操作或 JOIN。
- 复杂查询使用分页，避免一次性加载全表。
- 对频繁查询的字段建立索引，Trae 必须主动建议添加索引。

### 实体关系
- 使用 JPA/Hibernate 时，明确指定 `FetchType.LAZY`，避免 N+1 或级联加载过大。
- 双向关联必须有 `@JsonIgnore` 防止序列化循环。

## 六、前端开发规范（Vue/React）

### 组件拆分
- 单个组件不超过 300 行，超过必须拆分。
- 公共组件放在 `components/common/`，页面私有组件放在 `pages/xxx/components/`。

### 状态管理
- 全局状态使用 Pinia/Vuex，局部状态使用 ref/reactive。
- 避免直接修改 props，必须通过 emit 事件向上传递。

### API 请求
- 所有 API 请求统一放在 `api/` 目录下，按模块分类。
- 使用请求/响应拦截器统一处理 token、错误提示。

## 七、版本控制与协作

### 提交信息格式
- 格式：`<type>(<scope>): <subject>`
- type: feat | fix | docs | style | refactor | test | chore
- 示例：`feat(salary): 添加社保基数配置功能`

### GitHub 上传默认规则
- 当用户表达“上传代码”“把代码上传到 git”“推送到 GitHub”“提交并推送”等意图时，Trae 默认直接执行 Git 提交与推送，无需额外确认。
- 当前项目默认远程仓库为 `https://github.com/137490505/QHHRM.git`。
- 若本地仓库尚未初始化，Trae 必须自动执行 `git init`、配置 `main` 为默认分支，并将 `origin` 指向上述仓库。
- Trae 在提交前必须先检查 `.gitignore`、敏感配置和构建产物，避免将 `node_modules`、`dist`、`bin`、`obj`、日志文件、`.trae/tmp`、本地密钥和数据库密码上传到仓库。
- 若用户未指定提交信息，Trae 应根据本次改动自动生成符合规范的 commit message，然后执行 `git add`、`git commit`、`git push -u origin main`。
- 若推送失败仅因认证、网络或远程权限问题，Trae 应保留本地提交结果，并明确告知用户下一步处理方式，不得擅自更换仓库地址。

### 分支策略
- `main` 分支为生产环境代码，不得直接提交。
- 开发基于 `develop` 或 `feature/*` 分支，完成后发起 PR。
- 每次提交必须通过单元测试和代码格式检查。

### 代码审查
- 任何代码变更必须经过另一位开发者审查（除非单人项目）。
- Trae 在生成代码后应自动输出变更摘要，辅助人工审查。

## 八、性能与安全准则

### 性能
- 避免在循环中拼接字符串（应使用 StringBuilder）。
- 避免重复计算，使用缓存（如 Spring Cache、Redis）。
- 大对象（如 Excel 导出）使用流式处理，不得全量加载到内存。

### 安全
- 所有用户输入必须验证和过滤（防 XSS、SQL 注入）。
- 敏感数据（密码、手机号、身份证）必须加密存储（如 BCrypt、AES）。
- 接口必须做权限校验（如 Spring Security），不得依赖前端隐藏按钮。

## 九、交付前自查清单（Trae 必须执行）

在完成任何功能开发后，Trae 必须主动运行以下检查：
1. 所有新增/修改的方法都有单元测试且通过。
2. 代码中无 `System.out`、`console.log` 等调试输出。
3. 所有配置文件中的敏感信息已移除（如密码、密钥）。
4. 数据库变更脚本已放在 `db/migration` 目录（如使用 Flyway/Liquibase）。
5. 前端构建无警告（`npm run build` 无 error/warning）。
6. 已在本机或测试环境冒烟测试主流程。

## 十、如何让 Trae 应用这些规则

1. 将上述内容保存为 `.trae/rules/project_rules.md`。
2. 在 Trae 中开启 `Rules` 功能（设置 → Rules → 加载项目规则）。
3. 在 Chat 中对话时，规则自动生效。你也可以随时提醒：
   “请遵守项目开发规则进行修改”
